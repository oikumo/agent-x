## Vision + standing principle + main objectives

**Standing principle (non-negotiable): above the mechanics, not into them.**

v1's mechanical enforcement layer — 9 before-gates + 3 after-gates in `harness.ir.json`, the `gate_driver.ts` chain, TDD engine, KB/think/nav/ledger state — stays unchanged. meta_harness_2 is **read-only above v1**: it asks the harness questions; it does not add gates, mutate state, or change ledger semantics. The single *mechanical* touch is one clean refactor of `gate_driver.runBeforeGates` to accept a synthetic `GateCtx` and return decisions rather than throw — a behavior-preserving extension, not a redesign.

**The intelligence isn't in a query language.** It is in `op:plan` — the agent asks *"if I edit this file, what fires?"* and the harness answers with the gate chain evaluated against live state, before the block. That single op delivers the philosophical payoff the project exists to deliver: **the harness answers "what would happen if" before the agent acts.**

**(v1.4) Main objectives — the layer is justified by outcomes, not by the interrogative shape.** The layer earns its keep only if it measurably reduces (a) **opencode token consumption per session** and (b) **problem-solving wall-clock** — both re-anchored as first-class measured outcomes, not side-effects.

- **(a) Token consumption per session.** Today's per-session budget burn is dominated by re-derivation reads: WORK.md (startup) + scratchpad + `.projects/<feat>/CURRENT_STATE.md` (only 2 of 25 features have one) + ledger tail-greps + thoughts + fsm + nav queries for gotchas. Each session re-derives ~2–4 KB of prose the agent already wrote in a prior session. The harness writes the answer to most of these questions *to the ledger anyway* — but provides no single read to get it back. `omt_q{op:state}` collapses the 5-read resume ritual into 1 call; `omt_q{op:plan}` collapses the 3-step "edit→block→recover→retry" into 1 pre-flight; the U-set token-economy map (below) ties each *fold* to the tokens saved.
- **(b) Faster problem solving.** "Faster" decomposes into two axes: (i) **fewer sequential reasoning rounds** (the block→recover cycle is typically 2–3 turns per gated edit; `op:plan` pre-flights them away); (ii) **parallelism the agent is structurally not exploiting today** — `.agents/agents/` is empty, the `code-reviewer` agent is barely invoked, and `task{subagent_type:explore|general}` (fully parallel *out-of-main-context* research) appears **0 times** in `ledger-202608.jsonl` across 125 sessions. Every research round happens sequentially in the main context = full token cost in the context the user pays for. U16 makes this affordance visible so the agent can choose it.

**Verification anchor:** "reduce per-session tokens" is a verifiable outcome once `omt_q` is live — the `kind:"q"` telemetry records (v1.3) lets Phase-B measure multi-tool-call reduction, while a `kind:"q.token_economy"` sub-record (v1.4 candidate, see §Scope) can capture the actual `<tools_called> → <single_omt_q_call>` ratio pre/post. The wall-clock axis is a vibe-check today; a `kind:"q"` `latency_ms` field makes it measurable. **Both metrics post-date Phase-A**: the layer can only deliver the outcome once it exists.

An **interrogative layer above v1 mechanics** that collapses the agent's current pain patterns — verified from WORK.md, WORK_ARCHIVE.md (25 features + ~10 fix-sub-tasks DONE; 50+ rotations), all three ledgers (`ledger.jsonl` 19 + `ledger-202608.jsonl` 415 + `ledger-202607.jsonl` 538 = 972 records), and the 16 nav-indexed gotchas — into a single tool the agent consults instead of multi-tool reasoning rounds.

### What this project is **not**

- **Not a query language (at least not in Phase-A).** Grammar ships only in Phase-C, gated on evidence Phase-B usage demands it. v1 compliance with locked-scope realism: 12 of 13 use cases are fixed-shape questions parameterized by slug/path/session — they don't need a grammar.
- **Not a redesign of v1's process contract.** No gates added/merged/dropped; no phase FSM change; no TDD engine rewrite; no enforcer relocate (TS plugin stays TS plugin).
- **Not a replacement for the 8 `omt_*` tools.** `omt_q` is a 9th tool, read-only, that cross-cuts their substrates via three ops.
- **Not a removal of process discipline** — same harness, smarter consumers.
- **Not a TDD-cycle mutator.** `op:state` reports TDD position (U6) and TDD-close hygiene (U7) read-only; it does not drive `omt_tdd{op:green}` or `omt_complete` — the agent remains the actor.
- **Not a slug-normalization layer (owner of the slug-drift fix).** U8 *reports* slug drift + empty `feature`/`phase`; fixing it is a v1-process change (make `omt_phase.feature` required, validate `phase` against the FSM enum) — explicitly out of scope. U8 makes the *problem visible*, which is the first step to a v1 decision to canonicalize.

## Scope & success criteria

### In scope — Phase-A (one focused feature: `omt_q`)

Three ops on a new `omt_q` tool, all read-only above v1. The **core trio** (U1/U2/U3) is the v1-locked surface; U6–U11 + U13 are **folded ledger/IR projections** that deepen `op:state`/`op:plan` without requiring any new substrate (every field they read is already on the ledger or in a Python constant the harness already loads).

### Why this is realistic

Every atom `omt_q` consumes is something v1 already evaluates or already writes:
- `gate_driver.ts:evalPred()` already evaluates `path_in`/`file_has`/`session_flag`/`ledger_has`/`receipt_fresh`/`risk_high`/`cmd_match`/`fsm_allows` (the 8 preds in `harness.ir.json preds[]`) — `op:plan` calls the same evaluator with a synthetic ctx. (`cmd_match` is in the vocabulary but no live gate references it today — `op:plan` implements it for forward-compat, but no golden asserts a `cmd_match` block; see edge case #4.)
- `kb.ir.json` already contains records with `id`, `kind`, `src`, `line`, `layer`, `refs[]`, `tags[]` — `op:drift` self-joins on `id`; count drift is `len(records)` vs the live skeleton length.
- `omt_status` already projects session state (phase/hat/unlock/lint baseline); `op:state` cross-cuts it with the ledger tail and the thoughts index for a feature. `op:state`'s "current phase" sub-field is a direct pipe-through of `session_state.getActiveFeaturePhase(feature, session)` — that function already exists and already handles the session-exact-match vs 8h-window fallback.
- The `tdd` ledger payload (`state, test_node, target_src[], verified, exit_code, feature`, plus `done`-variant `checklist:{suite_passes, refactor_recorded, naming_ok}`) is already written by `omt_tdd` — `op:state`'s stranded-red derivation (U6) *and* TDD-close-hygiene (U7) are pure groupings of records already on disk. No TDD engine change.
- `KNOWN_SUITE_FAILURES` is a Python `frozenset` literal at `scripts/omt/tdd/state.py:132` — 6 explicit node IDs. U10 parses the literal (one regex over the file), it does not import/run `state.py`. The agent has no current way to ask "what's allowlisted?" without knowing this constant's path — exactly the interrogation gap.
- The receipt guard logic is `receipt_guard.ts:53 guardHarnessReceipt` (a one-liner around `omtHarnessE2eStatus(rel, abs)` from `omt_shared.ts`). U11 surfaces what that function already evaluates: `omt_harness_e2e_last_run.json`'s `passed_at` vs per-file mtime, plus the refresh test path (`@var e2e_test` = `tests/scripts/omt/test_omt_harness_e2e.py`) and refresh command (`@var e2e_cmd`).

**Build effort:** one TS plugin (~one feature), one clean extension to `gate_driver.ts`, one Python helper for the drift join (or pure TS over the IR JSON), one regex-knowledgeable extractor for `KNOWN_SUITE_FAILURES`.

### Edge cases (v1.1 + v1.2 — grounded in actual substrate inspection)

1. **`op:plan` projects before-gates only.** `harness.ir.json` has 12 gates; 9 are `on:"before"`, 3 are `on:"after"` (`g.mvc`, `g.tdd_after`, …). After-gates consume a *post-edit* snapshot (`hardSnapshot`, `refactorSnapshots`) that a pre-flight does not possess. `op:plan` filters `gates[].filter(g => g.on === "before")` and documents that after-gates are invisible to pre-flight. (Deferred `op:plan_after` in Phase-B addresses this with a hypothetical-edit shim around the MVC delta.)

2. **The TA:-literal self-trigger recursion.** `gate_driver.ts` itself contains 3 occurrences of the string literal `"TA:"` (the `file_has("TA:")` predicate implementation at lines 115–116, and the `g.think` gate stub at line 233). `g.think`'s `when=` is `file_has("TA:")`. **Editing `gate_driver.ts` triggers `g.think` on the very file that implements think-gate prediction.** Resolution: this is a *behavior*, not a bug — the agent must `omt_think{op:list, path:"gate_driver.ts"}` before editing it. The U2 golden query includes a `path=gate_driver.ts` scenario to prove `op:plan` and the real run agree on this self-referential case. The build of `op:plan` is gated by the think gate it is meant to predict — the agent would use `op:plan` to know to expect `g.think` *before* being blocked. The interrogative layer bootstraps itself.

3. **Thoughts line drift via `repaired_from`.** `thoughts.jsonl` records carry both `line` (intended TA: line) and `repaired_from` (the line the thought was *originally* attached to before a file edit shifted it). When a file is edited above a TA: thought, the thought's `line` becomes stale. `op:state`'s "risky thoughts on files touched under this feature" must report **both** the ledger `line` *and* a live re-scan of the source for the `TA:` marker (`@var thought_pattern`), flagging `line_drift=true` where they disagree. Without this, `op:state` would confidently report a thought at line 80 that the edit moved to line 92 — the exact silent staleness the interrogative layer exists to eliminate.

4. **`cmd_match` is a dead predicate in the current IR.** It's in `preds[]` and has an `evalPred` branch (`gate_driver.ts:134`), but no live gate's `when=` or `requires=` references it. `op:plan` implements it for forward-compat, but no golden asserts a `cmd_match` block.

5. **`op:drift` count-drift sign convention.** Count drift has two directions: (a) KB has *fewer* records than the source skeleton (under-curated — symbols exist in source with no KB record); (b) KB has *more* (over-curated — stale records for symbols since deleted). The plan locks: **(a) is NOT drift, just un-curated** (consistent with the v1 "new = not-yet-tracked is NOT drift" rule); **(b) IS drift** (gone symbols the AKB still references). The `feature_kb count drift` pre-existing failure is direction (b). The U3 golden asserts `op:drift` returns `count_drift: <positive int>` only when KB > skeleton, never the reverse.

6. **`op:state` phase fallback window.** `session_state.getActiveFeaturePhase` falls back from exact session match to "any phase record for this feature within `UNLOCK_WINDOW_MS` (28800000ms = 8h)" when the session ID isn't threaded through. `op:state` inherits this — a feature edited by a *different* session <8h ago will appear as "current phase = X" to a new session. This is the v1 single-user contract; `op:state` documents it but does not "fix" it (fixing it = a v1 redesign, out of scope).

The "canonical" slug is the most-recently-used one. This **reports but does not fix** the drift — canonicalization is a v1-process change (out of scope, per "not a slug-normalization layer").

The schema is fraying. `op:state`'s TDD-position derivation handles this by joining `tdd_testlist` to `tdd` records by `feature` (not session) — falling back across the 8h window consistent with v1's single-user assumption. The session-bleed is a v1 bug U8 surfaces but does not fix.

### Risks

1. **`op:plan`'s synthetic `GateCtx` is wrong → pre-flight diverges from actual gate behavior.** (Highest risk.) Mitigation: the U2 golden query asserts `op:plan`'s predicted chain == real `tool.execute.before` run on the identical path/session/tool. Drift between pre-flight and reality is a test failure, not a silent bug. The `gate_driver.ts` self-trigger scenario (#2) is the highest-signal canary.

2. **`op:drift` semantics settle late.** "Drift" needs a precise definition (moved-line tolerance, gone-symbol detection, NEW-but-not-in-KB). Mitigation: ship with the simplest defensible semantics (gone = no symbol at expected `src+line`; moved = symbol at a different `line` in same `src`; new = not-yet-tracked is NOT drift; count drift = direction-b only); refine per use case.

3. **HQL may never ship**, consuming the Phase-B/C ops as their own endpoints. Explicit in the plan — the language decision is *postponed to after evidence*, not committed upfront.

4. **The TA:-literal self-trigger recursion** (edge case #2) is the build order, not a paradox. **(v1.3)** Rather than framing `op:plan`'s self-prediction as a "could feel paradoxical" risk, the Phase-A build sequence makes it the first explicit step (see Tasks → Phase-A build → "Build-sequence bootstrap"): `omt_q{op:plan, path:"gate_driver.ts"}` predicts `g.think` → `omt_think{op:list, path:"gate_driver.ts"}` consult → edit. The interrogative layer constructs itself through its own prediction; this is the thesis paying off *during construction*, not after.

5. **Thoughts line drift** (edge case #3) could make `op:state` confidently report stale line numbers. Mitigation: live re-scan + `line_drift` flag; the U6/U1 golden scenario hand-crafts a post-edit line shift and asserts the flag fires.

6. **(v1.2) U10's `KNOWN_SUITE_FAILURES` parse breaks silently when `state.py` moves.** Mitigation: fail-open with a `KNOWN_SUITE_FAILURES_parse_failed` flag (edge case #10). Adding a drift test that pins the parse regex against `state.py` (sibling to `test_omt_docs_drift_pins.py`) catches moves. **This risk is the test, not the failure** — a parse failure surfaces immediately to the agent, unlike today's silent "the agent doesn't know the allowlist exists."

7. **(v1.2) U7's `closed_via_skip` derivation has false positives** — a `done` with `checklist.suite_passes:false` followed by `omt_skip{reason:"Override permits..."}` is the canonical escape, but the heuristic could misclassify a *different* feature's skip as the close. Mitigation: scope the join to the same `feature` + a temporal window (skip within 1h of the failed `done`); the U7 golden hand-crafts a cross-feature skip to assert it does NOT mark the wrong feature as `closed_via_skip`.

8. **(v1.2) U8's slug-canonicalization heuristic** could over-match (`feature_024` matching `feature_024.context_window_optimization` is correct; `feature_004` matching `feature_04` is not). Mitigation: the canonicalization matches the longest common prefix of known FEATURE.md dir slugs; the U8 golden hand-crafts a near-collision (`feature_024` vs `feature_024.x` variants — match; `feature_004` vs `feature_04` — no match).
