## Vision + standing principle + main objectives

**Standing principle (non-negotiable): feature-scoped gating beats repo-scoped gating.**

The evaluation's headline (§5, §6): *"the three P1 items are the workflow-evolution signal — they all share a common shape: **feature-scoped gating beats repo-scoped gating**. The phase lifecycle should gate on the FEATURE's content + hygiene, not on the union of all prior features' drift."* This is the v3 thesis. The harness's protective layers are mature (the evaluation's §2 lists 8 protections that caught real mistakes — resume discipline, node-granularity gotcha, think-gate consult, REFACTOR auto-revert, `harnessc check` hygiene budget, genuine-RED verification, the `omt_q` interrogative layer, two-hats enforcement). v3 does NOT touch those protections. It removes the *entanglement* that makes every feature's lifecycle depend on the union of all prior features' drift — the per-session tax that "discourages multi-session major features and makes any new ship blockable by any random prior drift."

**Main objectives — the project is justified by three outcomes:**

- **(a) Multi-session major-feature continuity — resume must be zero-tax.** Today, resuming a mid-flight feature hits three compounding costs: `omt_phase` silently resets the in-flight TDD cycle (§3.1, verified root cause in `state.py:157-169` + `get_tdd_state`), stranded-red closure is manual busywork (§3.2), and the phase-exit coverage gate re-opens prior finalized features' untested surface (§3.8). v3 makes "resume mid-GREEN" as cheap as "start fresh."
- **(b) Feature-done decoupled from repo-done — no more worldwide-drift triage per ship.** Today `omt_tdd{op:done}` runs the FULL suite via `run_full_suite` (`state.py:257-272`) and `cmd_validate_exit` (`gates.py:156-212`) blocks on any prior feature's drift — the evaluation calls this "the single worst design smell in the session" (§3.6). v3 splits `suite_passes` into `feature_suite_passes` + `repo_hygiene_passes` so a feature ships green-on-its-own-content and clean-hygiene, and prior drift is a separate repo-level triage concern.
- **(c) Preserve every protection that earned its keep — v3 removes friction, not safety.** The evaluation's §2 verdict: *"the harness's protections are NOT theoretical — at least 4 of them caught real mistakes or saved concrete rediscovery this session alone."* None of the §5 improvements removes a gate; each one either narrows a gate's scope (P1), adds an ergonomic op or convention (P2), or fixes a message/one-time cost (P3). The REFACTOR auto-revert guard, genuine-RED refusal, two-hats enforcement, and `harnessc check` hygiene budget all stay byte-identical.
- **(d) Token efficiency — pay for signal, not repetition (v1.2).** Measured against opencode.db (1009 agentx sessions): the harness's small costs are already lean (ceremony tools 257–369B/call; bootstrap tips once-per-session ~690B; schemas 1,094/1,280 budget) but three leaks are real — `omt_q{op:state}` dumps 24–36KB/call (T1), `omt_nav` answers uncapped at 4.5KB avg (T2), and context-compaction-driven duplicate re-reads (T3 — read = 66% of all tool-result bytes, worst case the same file 29× in one session). v1.2 merges T1–T3 into the build phases; T4 (schema budget at cap) becomes standing policy (D9). **Verification anchor (d):** T1 is verifiable by a golden asserting the default `state` envelope ≤ ~2KB (from 24–36KB measured) with `verbose:true` restoring the byte-identical full dump.

**Verification anchor:** (a) is verifiable per-fix — the P1 `omt_phase` idempotency fix is verifiable by re-running the exact §3.1 scenario (declare `omt_phase{phase:Programming, tdd:true}` on a feature with an in-flight GREEN/stranded-red cycle → assert TDD state preserved, not reset to `testlist`); (b) is verifiable by `omt_tdd{op:done}` succeeding while a synthetic prior-feature drift is present (feature's own tests green + hygiene clean → done; prior drift → repo-level triage note, not a block); (c) is verifiable by the P1/P2/P3 surface shipping zero gate removals — the e2e receipt round and the full regression suite (1223 baseline) stay green.

### What this project is **not**

- **Not a rewrite of v1/v2 mechanics.** The 9 gates + enforcer + TDD engine + IR compiler + `omt_q` interrogative layer stay. v3 changes *scope semantics* of existing gates (`suite_passes` → feature-scoped, coverage → diff-scoped) and adds *ops/conventions* (`omt_tdd{op:sync}`, structural-pin gotcha, date lint) — no gate is removed, no substrate is replaced.
- **Not a fix to the agent's misuse patterns.** The evaluation's LOCAL items that were the agent's own fault (e.g., not calling `omt_kb_nav` proactively before reading a file) are addressed only where a harness-side change removes the *recurrence* (P3 g.kb recent-read), not by re-architecting.
- **Not the feature_001/002 pending work.** Those remain scope-unset in WORK.md; v3 is a meta-harness project, home-owned in `.projects/meta/meta_harness_3/`, with feature-dir scaffolding deferred (see §Status).
- **Not a documentation exercise.** Every P1/P2 item is tied to a verified code anchor + a testable verification shape (see §Scope → Success criteria). The doc is the plan; the gates are the deliverable.

### Phase-A (the three P1 items — the "feature-scoped gating" core — + T1 token item, v1.2)

1. **`omt_phase` idempotent on in-flight features — via feature-scoped TDD state derivation.** Declaring `omt_phase` for a feature that already has an in-flight TDD cycle (within the unlock window) must PRESERVE the TDD state machine instead of resetting it to `testlist`. **Reframe (R3):** `omt_phase` is already idempotent at the ledger level (it appends a phase record); the reset is EMERGENT from `get_session_records` being **session-scoped**. The v3-consistent fix is to make TDD state derivation **feature-scoped** — the same thesis as P1-2/P1-3. `get_tdd_cycles(feature)` (`state.py:203`) is the existing precedent (reads all records for the feature, not session-filtered); `get_tdd_state`/`get_tdd_mode`/`get_current_test_node` should follow suit, resolving the active feature from the latest phase record (no `gate`/`after-edit` CLI change needed — they already pass `session`, which resolves to one active feature per session, matching the TS-side `getActiveFeaturePhase` model). The "warn before reset" option from the evaluation is a fallback band-aid, not the primary fix (it makes the reset visible without removing the entanglement). Anchor: `state.py:157-169` (`get_session_records`) + `state.py:181-192` (`get_tdd_state`) + `state.py:203-205` (`get_tdd_cycles` — the feature-scoped precedent). Success: re-run the §3.1 scenario — hermetic ledger with TWO session ids (prior session writes red+green records; new session writes only a phase record), declare `omt_phase{phase:Programming, tdd:true}` → assert TDD state shows the prior cycles (`cycles > 0`, stranded_red preserved), NOT `testlist`/`cycles: 0`.
2. **`suite_passes` → `feature_suite_passes` + `repo_hygiene_passes` — WITH a pre-feature baseline so real regressions still block (R4).** `omt_tdd{op:done}` gates on the feature's OWN test dir green + `harnessc check` hygiene clean + `KNOWN_SUITE_FAILURES` allowlist; full-suite drift of PRIOR features becomes a repo-level triage note, not a block. **Safety-critical addition (R4):** a naive split (feature's test dir only) would let a feature that BREAKS a prior feature's test (real regression) ship green — a protection regression that violates D5. The fix MUST distinguish DRIFT (prior test was already failing pre-feature) from REGRESSION (prior test was passing pre-feature, now failing). Mechanism: snapshot `baseline_failures` (the set of failing node IDs) at `omt_phase{phase:Programming}` entry, store in the phase ledger record; at `cmd_done`, `regressions = current_failures − baseline_failures − KNOWN_SUITE_FAILURES`. Regressions block `done`; drift does not. This mirrors the existing `KNOWN_SUITE_FAILURES` pattern (per-feature-baselined instead of global-hardcoded) and is the harness-consistent way to decouple without losing the regression catch. Anchor: `cli.py:233-243` (`cmd_done` + `run_full_suite` + `suite_clean`) + `state.py:132` (`KNOWN_SUITE_FAILURES`) + `phase_gate.ts:204-208` (phase record — add `baseline_failures` field). Success: `omt_tdd{op:done}` succeeds while a synthetic prior-feature DRIFT is present (prior test broken at baseline AND still broken → drift note, not a block); the SAME `done` BLOCKS when a prior test that was GREEN at baseline is now RED (regression) — the regression golden is the D5 guard.
3. **Coverage-gate scoped to THIS feature's diff (ADDED methods; MODIFIED needs a body-hash extension — R5).** `cmd_validate_exit`'s coverage scan checks only methods ADDED by this feature's diff, not ALL public methods of files the feature touched additively. **Two design decisions to lock at design time (R5):** (a) **Scope honesty** — the existing `diff_snapshots` (`state.py:232-237`) compares method-name SETS (`(class, method)` pairs) → detects ADDED methods only, NOT modified ones (same name, changed body). The plan v1.0 said "added/modified" using a mechanism that only does "added." Either scope P1-3 to "added methods" (matches existing mechanism, cheaper, honest) OR extend `extract_public_methods` (`ast_checks.py:89-114`) with a body-hash/line-range field so `diff_snapshots` detects modifications (more correct, more work). Recommendation: ship "added" in Phase-A (matches the GREEN-hat precedent), defer "modified" to a follow-up unless a Phase-A scenario demands it. (b) **Feature-baseline snapshot** — the per-edit `diff_snapshots` baseline is the LAST `cmd_green` snapshot (rolling, overwritten at `cli.py:174`), NOT the feature-baseline. At validate-exit, `load_snapshot` returns last-GREEN, not feature-start. To scope coverage to "methods added by THIS feature," capture a feature-baseline snapshot set at `omt_phase{phase:Programming}` entry (or first RED) — store per-feature alongside the existing `SNAPSHOT_DIR` — and diff against it at validate-exit. This is an EXTENSION of the snapshot substrate (a new feature-baseline tier), not a literal "promote the existing mechanism." Anchor: `gates.py:185-197` (full-file `find_untested_methods`) + `gates.py:129-131` (GREEN-hat `diff_snapshots` precedent) + `state.py:232-237` (`diff_snapshots` — added-only) + `ast_checks.py:89-114` (`extract_public_methods` — where a body-hash would go). Success: additive edit to a file with pre-existing untested methods (the §3.8 feature_024 surface) exits Testing WITHOUT requiring a `scope:all` skip; a NEW method added by the feature without a test reference still blocks.

T1. **`omt_q{op:state}` summary projection (v1.2 token item, user-approved shape: summary default + full flag).** The default `state` envelope returns counts + top-N (e.g., `slug_variants_count`, first 3 `empty_slug_records` with truncated `scope`); `verbose:true` restores the byte-identical full dump. Read-only op — no gate semantics touched (D8). Anchor: `omt_q.ts:494-528` (`decree_health` build + envelope assembly) + `omt_q.ts:164-171` (the `decree_health` type). Success: golden asserts the default envelope ≤ ~2KB (from 24–36KB measured) AND `verbose:true` restores the full dump byte-identical. **Receipt note:** `omt_q.ts` is harness surface — T1 appends to the R9 order as an independent 5th round (no dependency on state.py/gates.py/cli.py/phase_gate.ts rounds).

## Plan review (v1.1 — pre-build verification against the working tree)

> This section records the discrepancies + gaps found by re-verifying v1.0's anchors against the current code (2026-08-16, same commit as v1.0) and re-reading the evaluation evidence. ### Anchor corrections (factual)

- **R1 — P1-2 anchor mislocation (inherited from the evaluation).** The evaluation §3.6 states "`cmd_validate_exit` (gates.py:156) checks `suite_passes=true` which runs the FULL pytest suite." **Verified WRONG:** `cmd_validate_exit` (`gates.py:156-212`) checks ONLY dangling reds (173-183) + coverage gaps (185-197) + skip_override (161-171) — it never runs the suite. The full-suite run is in `cmd_done` (`cli.py:234` `run_full_suite` + `cli.py:243` `suite_clean`). v1.0's anchors happened to point to `cli.py`, but the §Purpose narrative echoed the evaluation's mislocation. **Implication:** `omt_tdd{op:done}` (`cmd_done`, cli.py) and `omt_complete`→validate-exit (`cmd_validate_exit`, gates.py) are TWO DISTINCT exit gates with DIFFERENT checks, called by DIFFERENT tools at DIFFERENT times. P1-2 (suite split) targets `cmd_done`; P1-3 (coverage-on-diff) targets `cmd_validate_exit`. The plan must not conflate them. (The evaluation's §3.6/§3.8 also blur this; v1.1 separates them.)
- **R2 — P3-9 substrate mischaracterization.** v1.0 said "mirror the `recent_consults` substrate (8h window) that g.think's U13 already uses." **Verified imprecise:** `recent_consults` (`omt_q.ts:251-285`) folds `think_consult` records — g.think's consult substrate — NOT KB-consult or Read events. The KB gate (`g.kb`, `gate_driver.ts:234`) uses `requires:"session_flag(kb_consulted)"` — a SESSION-LEVEL boolean (`session_state.ts:35` `kb: Map<session,{consulted:boolean}>`), set true after ANY `omt_kb_nav` call, not file-scoped, not recency-scoped. "Mirror recent_consults" would mislead an implementer to reuse the think-consult substrate. The actual fix needs a NEW per-file Read-recency record. Also: because `g.kb` is session-boolean, it's already a once-per-session cost (stops firing after the first `omt_kb_nav`) — the §3.4 event was the first-src-edit-before-any-consult case, so P3-9 is lower-leverage than v1.0 implied.

### Reframings (thesis consistency)

- **R3 — P1-1 reframe: "feature-scoped TDD state derivation," not "omt_phase idempotency."** v1.0 framed P1-1 as making `omt_phase` idempotent. But `omt_phase` (`phase_gate.ts:204-208`) is ALREADY idempotent at the ledger level — it appends a phase record, nothing resets explicitly. The TDD reset is EMERGENT from `get_session_records` (`state.py:157-169`) being **session-scoped**: a new session's phase record makes `mine` non-empty, shadowing the prior session's TDD records, so `get_tdd_state` (`state.py:181-192`) falls through to `testlist`. The v3-consistent fix is to make TDD state derivation **feature-scoped** — the same thesis as P1-2/P1-3. The precedent already exists: `get_tdd_cycles(feature)` (`state.py:203-205`) reads ALL records for the feature (not session-filtered); `cmd_validate_exit` and `cmd_done` already see cross-session feature history this way. The in-session functions (`get_tdd_state`/`get_tdd_mode`/`get_current_test_node`/`cmd_status`) are the only session-scoped outliers. The fix: resolve the active feature from the latest phase record (one active feature per session, matching the TS-side `getActiveFeaturePhase`), then derive TDD state from feature-scoped records within the unlock window. No `gate`/`after-edit` CLI change needed (they pass `session`, which resolves to the active feature). The "warn before reset" option from the evaluation is a fallback band-aid, not the primary fix.

### Gaps / missing design (safety + correctness)

- **R4 — P1-2 safety regression (the most important finding).** v1.0's P1-2 said "full-suite drift of PRIOR features becomes a repo-level triage note, not a block." But a naive split (feature's test dir only) would let a feature that BREAKS a prior feature's test (a real regression, not drift) ship green — removing the cross-feature regression catch that the current full-suite gate provides. **This violates D5 ("no protection regression").** The fix MUST distinguish DRIFT (prior test was already failing at feature start) from REGRESSION (prior test was passing at feature start, now failing). Mechanism: snapshot `baseline_failures` (set of failing node IDs) at `omt_phase{phase:Programming}` entry → store in the phase ledger record; at `cmd_done`, `regressions = current_failures − baseline_failures − KNOWN_SUITE_FAILURES`. Regressions block; drift doesn't. This mirrors the existing `KNOWN_SUITE_FAILURES` pattern (per-feature-baselined instead of global-hardcoded) and is the harness-consistent decoupling. **Mandatory Phase-A exit criterion:** a regression golden (prior test GREEN at baseline → RED now → `done` blocks).
- **R5 — P1-3 overclaim + baseline gap.** v1.0 said "methods ADDED/MODIFIED by THIS feature's diff (use `diff_snapshots`)." Two issues: (a) `diff_snapshots` (`state.py:232-237`) compares `(class, method)` name SETS → detects ADDED methods only, NOT modified (same name, changed body). The "modified" claim is not supported by the existing mechanism. (b) The per-edit `diff_snapshots` baseline is the LAST `cmd_green` snapshot (rolling, overwritten at `cli.py:174`), not a feature-baseline; at validate-exit `load_snapshot` returns last-GREEN, not feature-start. To scope coverage to "this feature's diff," the plan needs a FEATURE-BASELINE snapshot tier captured at `omt_phase{phase:Programming}` entry (or first RED), stored per-feature, and diffed against at validate-exit. This is an EXTENSION of the snapshot substrate, not a literal "promote the existing mechanism." Recommendation: ship "added methods" in Phase-A (matches the GREEN-hat precedent); defer "modified" unless a Phase-A scenario demands it (would require a body-hash field in `extract_public_methods`).
- **R6 — P3-8 robustness.** `HAT_RULES` is IR-derived (`gates.py:84-86` via `_derive_hat_rules`). The two-hats message fix must test `rules["src"]==False and rules["tests"]==False` (both blocked) rather than hardcode `state in ("testlist","done")`, so it stays correct if the IR hat config changes a state's allow-set. A golden with a synthetic IR hat config (a state with both blocked) proves config-driven behavior.
- **R8 — P2-4 location + state-mutation note.** The §5 table says "low (gates.py)" for `omt_tdd{op:sync}` — imprecise. The op is a NEW subcommand in `cli.py` (`cmd_sync` + dispatch registration), reusing `gates.py:173-183` dangling-red detection and writing a `green` record via `state.py:write_ledger`. Because sync writes a `green` record (state mutation), it must require the same test-passes condition as `cmd_green` and be a no-op if the test still fails — otherwise it could fabricate a GREEN and break the genuine-RED protection (§2.6).
