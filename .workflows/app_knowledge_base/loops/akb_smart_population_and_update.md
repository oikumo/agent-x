The application knowledge base (AKB) must stay populated comprehensively and reflect the live source code: every public class as a concept record, every curated overlay text meaningful, every drift caught. The agent should be able to drive a smart population/update pass — rebuild the skeleton, detect coverage gaps and drift, propose curation/fix alternatives — without hand-holding through the build steps.

This loop is the procedure for that pass. It is large-effort because the AKB is unbounded (ALL public classes, ~270+ records today plus deps plus curated docs), drift accrues continuously as `src/` moves, and "smart" means: AST skeleton + curated overlay + drift/coverage diagnostics + targeted curation proposals — not blind rebuild.

# Rules
1. Follow the omt methodology — the AKB is the canonical consumer of `omt_kb_nav` and the `g.kb` gate; opposing OMT in a workflow that polishes the KB would be self-defeating. Respect `omt_phase` before any `src/` or harness-surface edit, consult `omt_kb_nav` (the KB this loop is updating) before editing `.kb.omt` overlay or `scripts/omt/kb_*` code, and honour the think-gates on TA-carrying files.
2. Use omt_think everywhere an omt feature exists to put knowledge in the source code itself — when curating overlay records, when fixing `kb_ast_extract.py` / `kb_compiler.py` behaviour, and when patching the `g.kb` gate / `omt_kb_nav.ts` result bound.
3. Create automated unit tests whenever possible to verify the AKB pipeline (compiler build, AST extractor output, overlay-wins merge, orphan overlay-key warnings, stopword-lint exceptions); use mocks for filesystem and for `omt_kb_nav` query results. The existing `tests/scripts/omt/test_kb_*.py` (21 tests green as of 2026-08-08) is the pattern — extend, do not bypass.
4. Try to use sub-agents for parallel analysis whenever useful and possible — e.g. one sub-agent per subsystem (tools → agent facade → controllers → view partners → persistence → ui/tui) when authoring curated overlay text, or parallel drift/coverage diagnostics across siblings.
5. The AKB is the concept layer over source code (WHAT / WHY / CONNECTS-TO), never HOW — no full signatures, no field lists, no fallback-branch notes in records. Implementation lives in source; the record's `file:line` jumps there. Keep curated `text` ≤300 chars, non-human style, stopword-free (see `kb_compiler.py STOPWORDS`; `[a-zA-Z]+` regex splits snake_case so `is_*` / `can_*` / `should_*` identifiers trip the linter — reword into noun-phrases, never relax the linter).
6. Minimize future agent token consumption — this loop is the cure for "the agent must glob `.workflows/` and re-derive AKB state each trigger". Write the round's diagnostics and curation proposals to the nested-round sandbox artifact so a later session resumes by reading one file.

# AKB smart population and update strategy
1. Read the project documentation and the AKB contract — `.projects/meta/feature_kb_akb/PROJECT.md` (Standing principle: CONCEPTS not implementation; coverage = ALL public classes; index UNBOUNDED, query-bounded), its `Architecture` and `Implementation components` sections, and `.workflows/app_knowledge_base/META.md` (this subject's trigger keywords and output-path convention). Understand the two-tier pipeline: AST skeleton (`kb_ast_extract.py` over `src/agentx/**/*.py`) + curated overlay (`.meta/doc/omt++/code.kb.omt`) → merged by `kb_compiler.py build` → `.meta/.omt/kb.index.jsonl` + `kb.ir.json`.
2. Understand the current AKB state — run `uv run scripts/omt/kb_compiler.py build` (the canonical rebuild command) and read the round's counts + warnings + errors output (or, if a build already exists and `src/` since that build is unchanged, just query the live index via `omt_kb_nav`). Capture baseline numbers: total records, per-kind breakdown (`class` / `contract` / `dep` / `doc` / `flow` / `feature` / `pattern` / `xref` / `gotcha`), orphan overlay-key warnings, duplicate-id warnings, and any stopword / style-lint errors. ALSO use `omt_kb_nav` to probe known anchors (`nav "class.Agent"` → expects curated overlay text, not bare auto-text; `nav "class.ToolRegistry"` → expects overlay-wins; `nav "CONTRACT_" tag_type:TIER_CODE` → exercises the `MAX_RECORDS=25` truncate marker; `list_sections file:"<each subsystem>"` → coverage sanity). The goal of this step is a measured, not assumed, baseline.
3. Diagnose population gaps, drift, and curation debt — in parallel where possible (sub-agents per subsystem is the recommended shape), compare the rebuilt skeleton against: (a) coverage — every public class in `src/agentx/**/*.py` should have a skeleton record (target: 0 missing; the v2.1 coverage policy is ALL public classes, no significance filter — a `g.kb` consult must never hit a coverage gap for an edited file); (b) overlap-wins — every overlay entry in `code.kb.omt` should bind to a live skeleton id (orphan overlay-key → warning, must be resolved by rebinding or removing the entry); (c) auto-text ←→ curated — records still on auto-text (bases + abstractmethods only) are the curation queue, prioritised by subsystem traffic; (d) drift — `src/` classes renamed/removed since the last build surface as orphan overlay-keys and/or dangling refs; (e) duplicate-id warnings (4 are legacy/expected: `SessionDatabase`, `ChatMessage`, `IModelsViewPartner`, `MainTUIScreen` from `agent/view/tui`+`agent/persistence` vs `ui/tui`+`model/*` splits — confirm still legacy before ignoring); (f) gate/lint sanity — `g.kb` consult-gate wiring (SESSION_FLAGS `kb_consulted` + `kbTrack` + `state.kb` Map + `omt_kb_nav` writes the flag), `omt_kb_nav.ts` MAX_RECORDS cap + truncated marker, `@inject kb_bootstrap`. Record ALL findings in a new document or update an existing round document at `./sandbox/akb_smart_population_and_update/round_<NNN>_<BRIEF_DESCRIPTION>.md` — include the measured baseline numbers, the diagnosis table (subsystem × finding-type × proposed fix), and a recommended priority order for the user to pick from. This is the propose step; do NOT apply the curation yet.
4. Ask the user which curation / fix alternatives to perform this round — present the prioritised alternatives from step 3 (e.g. "curate the tools subsystem 5 record overlay text gaps" / "fix 3 orphan overlay-keys after the agent_controller.py rename" / "add 7 missing skeleton records for new ui/common helpers" / "patch `omt_kb_nav.ts` MAX_RECORDS bound per the per-query token budget" / "tighten the g.kb consult-gate path-aware bias"). The user picks one or more. This is the MANDATORY APPROVAL GATE — do not execute any fix, do not call any state-mutating tool on the chosen alternative until the user explicitly selects it. The propose document from step 3 is a sandbox artifact describing alternatives, not an applied change.
5. Execute the curation / fix alternatives chosen by the user — for each chosen alternative: if it touches `src/` or harness-surface (`scripts/omt/kb_*`, `.opencode/plugins/omt_kb_nav.ts`, `.opencode/lib/enforcer/*`, `META_HARNESS.omt`), declare `omt_phase` first and respect the receipt-round-robin (ONE edit per file per e2e receipt; `tests/scripts/omt/test_omt_harness_e2e.py -q` refreshes; the e2e test file itself is receipt-EXEMPT); for `.kb.omt` overlay edits, consult `omt_kb_nav` on the affected subsystem first (the KB this loop is updating is also the gate the loop must pass). Make automated unit tests (`tests/scripts/omt/test_kb_*.py` extended) green before rebuilding. After each landed change, `uv run scripts/omt/kb_compiler.py build` to refresh the unified index + IR, then re-probe with `omt_kb_nav` to confirm the fix took (overlay-wins for curated records; auto-text floor still intact for un-curated; orphan/dup warnings count reconciled with step 3's baseline). For harness-surface edits, run `harnessc build` after META_HARNESS edits and then the harness e2e to regenerate projections and refresh the receipt.
6. Update the results in the same file as step 3 — `./sandbox/akb_smart_population_and_update/round_<NNN>_<BRIEF_DESCRIPTION>.md` — with: what was executed per chosen alternative, the before/after record counts and per-kind breakdown, warnings resolved vs newly raised, the curated overlay additions/edits made (id → one-line text delta), any `src/` / harness-surface / test files touched (paths + one-line why), the post-build `omt_kb_nav` verification queries run and their results, and what is left to resume. The `# Result` section below is filled from these updates and allows a later session to resume by reading this one file (per `../META.md` §4.1 and §5.3 resumption/audit).
